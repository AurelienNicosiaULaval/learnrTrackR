# Controlled Course Pilot Protocol

This protocol is intended for a small, controlled course pilot of
`learnrTrackR`. It complements `pilot-checklist.md`.

The goal is to verify the teaching workflow, data flow, exports, and teacher
inspection process. It is not, by itself, an evaluation of learning gains.

## Pilot objective

Run one tracked tutorial with a small group of learners and verify that:

- learners can launch the tutorial with the expected identifier;
- tracked attempts are written to the selected database;
- teacher exports are complete and group-filtered correctly;
- the Moodle-ready CSV matches the intended cohort;
- the teacher report and dashboard support post-tutorial inspection;
- privacy and retention decisions are documented.

## Scope

In scope:

- one tutorial version;
- one configured course and tutorial identifier;
- one SQLite or PostgreSQL tracking database;
- one or more configured learner groups;
- teacher export files generated by `run-teacher.R` or the PostgreSQL smoke
  test;
- technical and workflow observations.

Out of scope unless a separate study protocol is approved:

- claims about learning gains;
- claims about improved engagement;
- claims about reduced grading workload at scale;
- comparisons between teaching interventions;
- publication of identifiable student records.

## Roles

- Instructor: owns the teaching activity, verifies questions, and inspects
  exports.
- Technical operator: prepares the database, launch environment, dashboard,
  and output directory.
- Data steward: confirms identifier choice, retention period, and access
  restrictions.
- Learners: complete the tutorial during the pilot window.

One person may hold several roles, but the decisions should still be recorded.

## Pre-pilot checklist

- [ ] The tutorial file has been frozen for the pilot.
- [ ] `config-csv/tutorials.csv` contains the correct tutorial id and version.
- [ ] `config-csv/questions.csv` matches every assessed question.
- [ ] `config-csv/students.csv` contains only necessary learner metadata.
- [ ] The chosen `student_id` is sufficient for Moodle matching.
- [ ] The selected database backend has been tested from a clean start.
- [ ] The output directory is outside Git and access-restricted.
- [ ] The Moodle CSV has been tested with a small sample or sandbox course.
- [ ] The dashboard is local or protected by the deployment environment.
- [ ] The retention period for attempts, exports, and reports is documented.
- [ ] Ethics or privacy review requirements have been checked before using
      pilot data for research or publication.

## Launch procedure

1. Install or update `learnrTrackR`.
2. Copy `student.env.example` to `student.env` for local rehearsal, or prepare
   equivalent environment variables in the deployment system.
3. Set `LEARNRTRACKR_DB`.
4. Set `LEARNRTRACKR_STUDENT_ID` for each learner session.
5. Set `LEARNRTRACKR_GROUP_ID` when group-specific inspection is needed.
6. Launch the tutorial with `Rscript run-student.R` or the managed deployment
   command.
7. Ask learners to complete the selected tutorial during the pilot window.

## Teacher inspection procedure

1. Copy `teacher.env.example` to `teacher.env`, or prepare equivalent
   deployment variables.
2. Set `LEARNRTRACKR_DB` to the same database used by learners.
3. Set `LEARNRTRACKR_GROUP_ID` if only one cohort should be inspected.
4. Run `Rscript run-teacher.R`.
5. Inspect:
   - `course-pilot-attempts.csv`;
   - `course-pilot-scores.csv`;
   - `course-pilot-gradebook.csv`;
   - `course-pilot-moodle.csv`;
   - `course-pilot-teacher-report.html`;
   - `course-pilot-bundle/`.
6. Confirm that no unexpected learner appears in the Moodle CSV.
7. Import into Moodle only after the identifier mapping is verified.

## Technical success criteria

The pilot is technically successful if:

- at least one attempt is recorded for each participating learner who submits
  an answer;
- attempt numbers increase correctly for repeated submissions;
- all expected questions appear in the gradebook;
- unanswered registered questions are represented in the gradebook;
- group-filtered exports exclude learners from other groups;
- the Moodle-ready CSV has one row per exported learner;
- the teacher can reproduce the export from the database and recorded
  configuration.

## Evidence boundaries

The following evidence can support a software or workflow report:

- the package version and Git commit;
- configuration files used for the pilot;
- aggregate counts of learners, attempts, questions, and export rows;
- technical issues encountered during launch or export;
- teacher notes on usability and missing features;
- anonymised or pseudonymised summaries when allowed by the local data plan.

The following claims require a separate evaluation design and appropriate data:

- learning gains;
- improved retention;
- improved student engagement;
- reduction in grading workload;
- superiority over another teaching method.
